# 火災保険 有責・無責 判定シート

損害保険代理店・窓口の担当者が、火災保険の事故連絡を受けたその場で、有責・無責の見込みと理由をお客様に説明できるようにするブラウザアプリです。

- **公開サイト**：https://crowchamp-ui.github.io/fire-insurance-judge/
- **リポジトリ**：https://github.com/crowchamp-ui/fire-insurance-judge
- **仕様書（最終版）**：[docs/spec.md](docs/spec.md)

> 一般的な住宅火災保険の約款をもとにした目安です。最終的な支払可否は保険会社が決めます。事例はすべて架空です。

---

## 1. 何を作ったか（Core／Why／What／How）

| 層 | 内容 |
|---|---|
| **Core** | 窓口での案内の誤りを減らし、お客様に「最初に聞いた話と違う」と思わせない |
| **Why** | 代理店・窓口の担当者が、事故の連絡を受けたその場で、約款を調べなくても有責・無責の見込みと理由をお客様に説明できる状態にする |
| **What** | 契約内容と事故の状況を入力すると、有責／無責／要確認の見込みと、項目ごとの判定理由が出る判定シート。お客様向けの説明文をコピーでき、案内の訂正件数を数える利用ログを持つ |
| **How** | HTML／CSS／JavaScript だけのブラウザアプリ。サーバーを持たず、GitHub Pages で公開 |

**対象者**：火災保険の事故連絡を最初に受ける代理店・窓口の担当者（保険の専門家ではなく、約款の細かい条件までは覚えていない）

**解決したい困りごと**
1. お客様への説明：「保険は出ますか」と聞かれても、その場で答えられない。無責になりそうな場合に、なぜ出ないのかをうまく説明できない
2. 約款を調べる手間：補償の範囲や免責の条件を、約款から探すのに時間がかかる

**成功を測る数字（KPI）**：案内の訂正件数（窓口で伝えた見込みと保険会社の最終判断が、有責↔無責で食い違った件数）。毎月末に、導入前1か月と導入後1か月を比べる。

詳しくは [docs/課題仮説シート.md](docs/課題仮説シート.md)。

## 2. 仕様書

最終版は [docs/spec.md](docs/spec.md)。主な機能は次のとおりです。

| 機能 | 内容 |
|---|---|
| 判定 | 請求期限 → 保険期間 → 保険の対象 → 免責事由 → 補償範囲 → 原因ごとの支払基準 → 支払額の順にチェックし、有責／無責／要確認と理由を表示する。入力を変えるとその場で更新 |
| 原因ごとの追加質問 | 風災なら「建物の外側に破損があるか」、水災なら「床上浸水・地盤面から45cm超か」など、判定を分ける質問だけを出す |
| お客様向けの説明文 | 判定結果から、メール・手紙の本文に貼れる説明文（事故の概要・見込み・理由・最終判断は保険会社であること）を作り、コピーできる。金額は入れない |
| 利用ログ | 案内した判定を記録し、あとから保険会社の最終判断を入力すると「案内の訂正」を自動で数える。CSV で書き出せる。個人情報は記録しない |
| 架空の事例 | 6つの事例ボタンで、すぐに動きを試せる |

## 3. 現状と今後

### できていること

- 仕様書（spec.md）の受入基準をすべて満たしている。自動テスト19件がすべて合格し、画面の動きはブラウザで確認した（[docs/test.md](docs/test.md)）
- GitHub Pages で公開し、公開したサイトでも同じように動くことを確認した
- 公開前チェック（第6週 P34）を確認した。規制分野（金融）に当たるため、架空の事例だけを載せた PoC として公開し、「最終判断は保険会社」である旨を常に表示している

### まだできていないこと・課題

- **成功の数字はまだ測れていない**：利用ログの仕組みはできたが、実際の窓口業務ではまだ使っていない。導入前の訂正件数も記録できていない
- **判定は一般的な約款の基準**：保険会社や商品ごとの違い（免責の内容、風災の支払方式など）は、手で設定を変える必要がある
- **費用保険金は計算しない**：臨時費用保険金・残存物取片づけ費用などは対象外
- **地震保険は対象外**（下の「開発の中で見直したこと」を参照）
- **利用ログは1人用**：記録はそのパソコンのブラウザ内だけにあり、複数人で集計できない

### これからの改善の順番

1. **自分で1か月使う**（第6週 P10）：実際の事故受付で使い、いつ・どの事故で使ったか、どこで迷ったかを記録する。あわせて、導入前の訂正件数を課題仮説シートに記入する
2. **月末に KPI を見る**：利用ログの「案内の訂正」の件数を、導入前と比べる。減っていなければ、Why か What を疑う（第6週 P23）
3. **ほかの担当者に説明せずに渡す**：最初の数分でどこで操作が止まるかを観察し、画面を直す
4. **集まった要望を、なぜその要望かまで確かめてから取り込む**：候補は「保険会社ごとの約款設定の切り替え」「費用保険金の計算」
5. **複数人で使うことになったら**：利用ログを Google スプレッドシートなどに集める仕組みを検討する（その場合は個人情報と記録への同意を改めて確認する）

## 4. 開発の進め方と工夫

### 仕様書と実装を対応させた

- 仕様書（spec.md）・作る順番（wbs.md）・背景（課題仮説シート.md）を会話の外にファイルとして置き、AI への指示ファイル（CLAUDE.md）に「機能を直したら spec.md と wbs.md にも反映する」と書いた
- spec.md の受入基準を、そのまま自動テスト（`tests/judge.test.mjs`）と確認記録（`docs/test.md`）に対応させた。機能を足すたびに受入基準・テスト・記録を一緒に増やした

### 試行錯誤と検証

Git のログ（16コミット）に、機能ごとの「作る → 確かめる → 直す → 記録する」の流れが残っている。

- **テストが本当に効いているかを確かめた**：判定をわざと壊すと、テストが失敗することを確認してから元に戻した
- **ブラウザで確かめて、不具合を2回見つけた**：スマホ幅（400px）で画面がはみ出す不具合を2回見つけ、どちらも直して再確認した
- **AI の「確認しました」を鵜呑みにしなかった**：AI が確認できない部分（普段のブラウザでのコピー、Excel で開いたときの文字化け）は自分で試し、結果を記録した

### 開発の中で見直したこと（What の見直し）

最初は地震保険の損害区分（全損・大半損・小半損・一部損）を入力すると、支払額を計算する機能を持っていた。しかし実務の経験から、次のことに気づいた。

- 窓口が本当に知りたいのは区分の判断だが、区分は保険会社の調査員・鑑定人が、非公開の点数表で現地査定して決める
- 区分さえ分かれば、地震保険は定率払いなので、ツールを使うまでもない
- 区分を窓口で予想して伝えると、外れたときに案内の訂正になり、Core に反する

そこで、Core と Why はそのままにして **What を見直し**、地震保険の判定をなくした。地震・噴火・津波による損害は「火災保険では補償されない」とだけ判定し、地震保険の窓口へ案内する（[課題仮説シートの「見直しの記録」](docs/課題仮説シート.md)）。

### AI 開発の課題への対処

| 課題 | 対処 |
|---|---|
| AI が勝手に推測で埋める | 1機能ごとにプランモードで計画させ、不明点（説明文の使い方、金額を入れるか、訂正の数え方など）は作る前に質問させて自分で決めた |
| まとめて頼むと品質が落ちる | wbs.md の1項目を1回の依頼とし、1機能ごとに確認してコミットした |
| 何を測るかを AI が決めてしまう | 成功の数字（案内の訂正件数）と、訂正として数える範囲（有責↔無責だけ）は自分で決めた |
| 秘密・個人情報の流出 | 個人情報を入力・記録しない設計にした。公開前にコミットの作成者のメールアドレスを GitHub の匿名アドレスに差し替えた。非公開の地震保険の点数表は使わなかった |
